# 按需虚拟屏优先用 prep-cmd 切换现有 MTT VDD，不换 SudoVDA

**TL;DR**：驱动选型仍是不换栈（继续用已验证的 MTT VDD，不引 SudoVDA）。但**切屏方式已改判**：`global_prep_cmd` 这条路实测走不通——它在 `configure_display` 与 `probe_encoders` 之后才执行，而且 `dd_configuration_option = disabled` 会触发后台回滚，两者叠加把连接卡死在编码器探测阶段。现在用 Sunshine 自己的 `ensure_only_display` + `output_name` 指向虚拟屏，虚拟屏设备常驻启用但不占桌面。失败证据见 [prep 命令改不了捕获屏](prep命令改不了捕获屏.md)。

## 为什么要换掉 ensure_only_display

当前 vdd 基线用 `dd_configuration_option = ensure_only_display`：Sunshine 在会话开始时切屏、断开时回滚。这正是"连接才拉起"的语义，但 [显示拓扑卡死](显示拓扑卡死.md) 记录了它的失败路径——回滚时目标设备已不在拓扑里，进入每 5 秒一次的无超时重试，把会话拆除线程堵死约两分钟。

正确分工见 [虚拟显示器方案](虚拟显示器方案.md)：切屏发生在连接之前，Sunshine 只捕获一块已经存在的屏。会话级钩子让这件事可以自动化，而不需要手工干预。

## Sunshine 提供了什么

`global_prep_cmd` 是 Sunshine 的全局会话钩子（也可按 app 配置）：

```text
global_prep_cmd = [{"do":"...","undo":"...","elevated":false}]
```

- `do` 在串流启动前执行，`undo` 在会话结束后执行；
- 任何一个 `do` 返回非零，Sunshine 取消本次串流（见 issue #2872）；
- 环境变量 `SUNSHINE_CLIENT_WIDTH` / `HEIGHT` / `FPS` / `HDR` / `NAME` 会传给命令——这是"按客户端分辨率拉起"的依据；
- **已知坑**：Windows 登录屏幕（无人登录）时 `QueryUserToken` 失败，prep 命令会 `Permission denied`；issue #6024 在 2026.914 上复现，2026-11-02 已在预发布修复。**本机停在 2026.516 老架构，尚无此问题的报告，但也没有做过无人登录实测**——不声明免疫。

## 两条路线对比

| 维度 | MTT VDD + 外部 prep 脚本 | vdisplay (SudoVDA) |
|---|---|---|
| 驱动成熟度 | 上游 VirtualDrivers/Virtual-Display-Driver，本机已验证安装、分辨率预设、无 BOM 解析 | Apollo 同款 SudoVDA，随 vdisplay.exe 内置 |
| 项目年龄 | 持续维护，本机报告日期 2026-11-24 | 首个 release `v0.1.0` 发布于 2026-10-08，只有一个版本，750 次下载 |
| 会话清理 | `undo` 脚本负责；脚本没跑到就需要 [恢复显示.cmd] 兜底 | SudoVDA watchdog 3 秒：无 ping 即移除所有虚拟屏并恢复物理屏，daemon 崩溃/Sunshine 退出也能清理 |
| 分辨率 | 预设在 `vdd_settings.xml`，客户端档位必须命中预设模式 | 按 `SUNSHINE_CLIENT_*` 动态创建，任意分辨率 |
| 切换权 | 外部脚本，符合仓库原则 | 外部工具 prep 命令，同样在 Sunshine 之外 |
| 换机成本 | 沿用现有 zip 与 manifest | 要新增组件、锁哈希、导入证书、卸载/替换现有 MTT VDD |
| 失败模式 | 最坏是物理屏没恢复，可双击救援脚本 | watchdog 兜底；但 `uninstall-driver` 会连带停掉 Apollo 的虚拟屏 |

**判断**：vdisplay 的 watchdog 是真正的稳定性优势——它把"断开后必须恢复"从脚本责任变成驱动责任。但本机 2026.516 的目标是先做到可复现、可回滚；换驱动会同时引入"新驱动 + 新工具 + 新证书 + 新旧驱动共存"四个变量，违背 [分支选型](分支选型.md) 里"一次只解决一个现象"的原则。等这台机器的连接—断开循环稳定后，再评估是否换。

## 现行方案（Sunshine 原生 ensure_only_display）

1. 虚拟屏**设备常驻启用**（`ConfigFlags=0`）——`probe_encoders` 必须能枚举到它，否则连接失败。
2. 桌面拓扑平时只留物理屏：`DisplaySwitch /internal`。虚拟屏存在但不占桌面，视觉上等价于"没连接时没有虚拟屏"。
3. `sunshine.conf`：

```text
dd_configuration_option = ensure_only_display
dd_resolution_option = auto
dd_refresh_rate_option = auto
output_name = \\.\DISPLAYn        # 虚拟屏编号，取值见 dxgi-info
# 不写 global_prep_cmd
```

4. 连接时 Sunshine 在 `configure_display` 阶段切到虚拟屏（早于编码器探测，时序正确）；断开时回滚物理屏。
5. 分辨率：静态表 `vdd-resolutions.txt` 覆盖 720p / 1080p / 1440p / 4K 与 16:10 常用档；表外档位会静默失败，所以新增客户端时先补表。

## 已否决：prep-cmd 外部切屏（2026-11-24 实测）

曾实现 `Switch-Vdd.ps1` + `Install-OnDemand.ps1`，由 `global_prep_cmd` 在会话前后切屏。单独跑脚本能成功，但**真实连接失败**：Sunshine 的 prep 在 `configure_display` 和 `probe_encoders` 之后才执行，而且 `dd_configuration_option = disabled` 会触发后台 `revert_configuration()`，两者叠加把探测卡死。

失败日志与源码依据见 [prep 命令改不了捕获屏](prep命令改不了捕获屏.md)。相关脚本与入口已从包内移除，避免误用。

## 本机实测（redmibookpro15x，2026-11-24）

| 动作 | 结果 |
|---|---|
| 虚拟屏安装 | `ROOT\DISPLAY\0001` Status=OK；单屏需 `DisplaySwitch /extend` 才进 DXGI |
| 设备级禁用后连接 | **失败**：日志卡在 `probe_encoders`，无 `Executing Do Cmd`、无会话 |
| 设备常驻启用 + `ensure_only_display` | 配置已就绪，等待真实客户端复测 |

**仍未验证**：`ensure_only_display` 的实际连接—断开循环。2026.516 的 Web API 没有 launch 端点（`confighttp.cpp` 只有 `GET/POST /api/apps`、`DELETE`、`/api/apps/close`），无法用 API 模拟 Moonlight；本机也未配对客户端。

## 怎么验证

1. 不连接时：DXGI 只有 `\\.\DISPLAY1`；虚拟屏设备 `ConfigFlags=0` 但 `Attached=no`。
2. 连接后：`sunshine.log` 出现 `New streaming session started` 与 `CLIENT CONNECTED`；虚拟屏 `Resolution` 等于客户端请求值。
3. 断开后 10 秒内：物理屏恢复，虚拟屏回到 `Attached=no`。
4. 若连接后黑屏且 30 秒不恢复：`Win+P` 选「仅电脑屏幕」，或双击 `恢复显示.cmd`。
