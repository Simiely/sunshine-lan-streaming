## 现象

按设备把 `C:\VirtualDisplayDriver\vdd_settings.xml` 改成 6 个分辨率（含 iPad 的 2732x2048@120），
`sunshine.conf` 的 `output_name` 也指向虚拟屏。但 DXGI 枚举出来永远是 `800x600`。

容易误判成"驱动没读到文件"或"需要重启电脑"，于是反复做下面这些**全部无效**的尝试。

## 三个很有欺骗性的假象

### 假象一：禁用/启用设备看起来像重建了

`pnputil /disable-device` + `/enable-device` 会让 `\\.\DISPLAYn` 的**编号变化**（43 → 44），
看起来设备栈确实重建了。但 UMDF 宿主进程没退出，驱动 DLL 仍在内存里，
解析失败的结果也就一直是那个空的 `monitorModes`。**编号变 ≠ 配置重读**。

### 假象二：重装驱动也无效

`pnputil /remove-device` + `devcon install` 确实销毁并重建了设备实例（编号 44 → 45），
但依然 800x600。原因同上是文件本身解析不了，重建多少次都读不进来。

顺带排除一个误解：**不需要走 VDC 图形界面安装**。
官方 `Community Scripts/virtual-driver-manager.ps1` 的 install 就是
`devcon install MttVDD.inf "Root\MttVDD"`，与脚本做法一致，而且它不复制也不处理配置文件。

### 假象三：日志说"Using vdd_settings.xml"，像是读成功了

这句话只在 `loadSettings()` 走完整个解析循环后才会打印（源码 L1631），
但 `SetInput` 失败、`Read` 中途失败、`stoi` 抛异常等路径都是**静默 return**，
其中只有部分分支写了 error 日志。所以"看到这句话"不等于"模式加载成功"，
必须看 `Output target modes count` 和逐条 `Added:`。

## 根因

源码 `MttVDD/Driver.cpp`（25.7.23）中：

```cpp
hr = SHCreateStreamOnFileW(filename.c_str(), STGM_READ, &pStream);
hr = CreateXmlReader(__uuidof(IXmlReader), (void**)&pReader, NULL);
hr = pReader->SetInput(pStream);        // 没有指定编码
```

`IXmlReader::SetInput(IStream)` 不会主动嗅探并跳过 UTF-8 BOM。
而 `XmlDocument.Save($path)` 在 PowerShell 里默认输出 **UTF-8 BOM**。

对比实证：

| 时间 | 文件 BOM | 结果 |
|---|---|---|
| 16:18 | 有 | 800x600 |
| 16:37 | 有 | 800x600（重建过） |
| 16:53 | 被驱动自身用 XmlLite 重写 → 无 | — |
| 16:54 | 无 | 1920x1080，12 个模式全部加载 |

16:53 那一步只是通过命名管道发了 `LOGGING true`，驱动用 `UpdateXmlToggleSetting`
重写了整个 XML，顺带把 BOM 去掉了。**变量只有 BOM 一项**。

## 诊断手段（驱动自带，不用猜）

命名管道 `\\.\pipe\MTTVirtualDisplayPipe`，发送 **UTF-16LE** 编码的文本命令
（驱动按 `wchar_t` 读取，发 UTF-8 会得到乱码而被忽略）：

| 命令 | 作用 |
|---|---|
| `LOGGING true` | 开启日志，写入 `C:\VirtualDisplayDriver\Logs\log_YYYY-MM-DD.txt`，并回写 XML |
| `LOG_DEBUG true` | 开启 debug 级，会逐条打印 `Added: WxH @ N/D Hz` 与模式总数 |
| `RELOAD_DRIVER` | 重建适配器，但**不会重读 XML**（`InitAdapter()` → `maincalc()` 只重载 EDID） |

关键日志行：

```
[INFO]  VDD Path: C:\VirtualDisplayDriver
[INFO]  Using vdd_settings.xml
[DEBUG] Added: 2732x2048 @ 120/1Hz
[DEBUG] Output target modes count: 12
```

`Output target modes count` 等于「分辨率数 × 各自刷新率 + 分辨率数 × 全局刷新率」。
6 个分辨率 + 全局 60 一档，就是 12。

## 一个容易继续误判的点

配置生效后，虚拟屏的**初始分辨率仍然是 800x600**，不要因此以为又失败了。

`GetDefaultModes` 直接返回 `STATUS_NOT_IMPLEMENTED`，模式来自
`ParseMonitorDescription`，而 Windows 的初始选择受 hardcoded EDID 的描述符影响。
`PreferredMonitorModeIdx = 0` 只是建议值。

只要 `Output target modes count` 覆盖了目标分辨率，`dd_resolution_option = auto`
就能在客户端接入时切过去。判断标准是**模式列表**，不是当前分辨率。

## 正确做法

1. 写入用无 BOM（`XmlWriterSettings` + `UTF8Encoding($false)`）
2. 写前检查前 3 字节，带 BOM 就无条件重写（不能依赖"内容有变化"才写）
3. 配置确有变化时，用「移除设备节点 + devcon 重建」让 `loadSettings()` 重新执行
4. 重建后 `\\.\DISPLAYn` 编号必变，`output_name` 要重新识别并绑定
5. 不要用「当前分辨率等于配置第一项」判断是否生效——这个判据必然误报
