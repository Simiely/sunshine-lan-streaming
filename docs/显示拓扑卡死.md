# 用 ensure_only_display 会让断开串流时卡死两分钟

**TL;DR**：卡死不是切换失败造成的，是"失败后必须恢复原状"的阻塞重试造成的。让它别管拓扑，问题就不存在。

## 现象

退出串流（`Ctrl+Alt+Shift+Q`）后主机冻结约两分钟：画面停在最后一帧、Sunshine 不再接受新连接、随后 Windows 服务自动重启它。多显示器环境下，物理屏的分辨率可能停在串流时的虚拟分辨率。

## 根因

日志是决定性的：

```text
Error: Device {f8a543aa-...} does not exist in the available path source data!
Error: Failed to change topology to: [ [ "{f8a543aa-...}" ] ]
Info: Trying to revert applied display device settings. API is available: false
Info: Trying to revert applied display device settings. API is available: false   ← 每 5 秒
```

三步因果：

1. 会话开始时 Sunshine 用 `ensure_only_display` 把桌面切到只剩目标屏
2. 会话结束时回滚，但目标设备（虚拟屏卸载 / 显示器休眠 / 驱动重置）已不在拓扑里
3. 回滚失败后进入固定间隔重试，**重试发生在会话拆除线程上**，于是整个拆除被阻塞

关键在于第 3 步：Windows CCD API 失败是常态，问题在于把"恢复原状"实现成了阻塞式循环，而且没有超时。

## 规避

| 做法 | 风险 | 说明 |
|---|---|---|
| `dd_configuration_option = disabled` | 几乎为零 | 切屏交给外部脚本或手动 `Win+P`，Sunshine 只负责捕获固定的那块屏 |
| `ensure_primary` | 低 | 只改主屏归属，不删除其他屏 |
| `ensure_only_display` | **高** | 就是本文的复现条件 |

配套要求：`output_name` 固定指向一块**始终存在**的屏。如果指向虚拟屏，必须保证虚拟屏在 Sunshine 启动前就存在，否则等于换了个方式触发同一条失败路径。

## 怎么验证

1. 触发一次完整的连接—断开循环。
2. 在日志里搜 `Trying to revert applied display device settings`，正常应出现 0 次或 1 次；出现 ≥5 次即为命中。
3. 同时观察断开到可再次连接的时间，正常应在数秒内。

## 边界

这条路径在 2026.516 里同样存在，只是报告少。换老版本不等于免疫——**只有把拓扑管理的发起权拿走才算真正规避**。
