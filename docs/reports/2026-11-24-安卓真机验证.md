# 真机通了，但不是走局域网通的

**TL;DR**：手机真的连上来并串流了，`hevc_nvenc` / `2560x1440` / `60fps` / Opus 音频 / 虚拟触屏 + Xbox 360 手柄全部正常。但**手机连的是宿主自己开的移动热点**（`192.168.137.0/24`），不是业务网段 `10.4.240.0/23`。所以"真机串流"成立，"局域网串流"没被验证。同一次测试还抓出两个问题：三个基线配置键被二次清空，HAGS 处于开启状态。

> 一次性记录，`status: active`（后续拓扑验证完成后再归档）。清单项定义见 [配置清单](../配置清单.md)。

## 三、成立与不成立

**成立（L2/L3 的客户端侧）**：真机配对、会话建立、硬件编码、音频、触屏输入、手柄识别全部跑通。`output_name` 修复有效——上次的黑屏确实是 `Offset` 落在虚拟桌面另一半导致的，与 HDR 无关。

**不成立（L3 的拓扑侧）**：`D-01` 与 `I-03` 都要求客户端与宿主同处一个广播域。实测客户端在 `192.168.137.0/24`，宿主业务口在 `10.4.240.0/23`，两者靠宿主自身路由直连，**不经过路由器**。后果有三：
1. 体验好是"直连无线网卡"的红利，不是局域网方案的上限；
2. 换一台没开热点的机器照抄这套配置，复现不出来；
3. 手机离开热点覆盖范围就断，不具备"在家任意位置串流"的能力。

要补这一环，得让 `findx9pro` 接家庭路由器的 Wi-Fi，再走一遍。此项未完成前，本仓库不得对外声明"局域网串流已验证"。

## 四、两个问题

### 4.1 三个基线配置键二次丢失

测试期间 `sunshine.conf` 变成 41 字节，只剩：

```
locale = zh
output_name = \\.\DISPLAY1
```

`origin_web_ui_allowed`、`upnp`、`dd_configuration_option` 全部消失，对应 `D-02` / `D-03` 从 ✅ 退回 ⚠️，体检总数从 14 合格掉到 12 合格。`upnp` 回落到默认 `enabled` 意味着宿主重新允许向路由器请求端口映射——这是安全暴露，不是审美问题。

根因是 Sunshine 的 `POST /api/config` **整体替换**配置而非增量合并：任何一次只提交部分键的写入，都会把未提交的键抹掉。处置方式改为直接对 `sunshine.conf` 做合并写回，见 [配置写入覆盖](../配置写入覆盖.md) 与 `payload/scripts/Restore-Baseline.ps1`。

### 4.2 HAGS 开着

注册表 `HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers\HwSchMode` **不存在**，而 Win11 缺省即视为开启，日志也明确打印 `Active GPU has HAGS enabled`。原先体检把"键不存在"判为 `❓ 未设置` 是错的，已改为按缺省值判定并降级为 ⚠️。Sunshine 自己会对这一项发警告，它与串流编码的兼容性问题需要在稳定性测试里单独观察。

## 六、顺带确认的客户端选型

| 客户端 | 包名 | 能否与官方版并存 | 主机侧依赖 |
|---|---|---|---|
| 官方 Moonlight | `com.limelight` | — | 无 |
| `moonlight-axixi` | `com.limelight.unofficialA` | 可，与其余三者都不撞 | 基础串流只需官方 Sunshine |
| Artemis | `com.limelight.unofficial` | 可，但与 Desktop Mode 互斥 | 虚拟显示器需 Apollo |
| Desktop Mode | `com.limelight.unofficial` | 可，但与 Artemis 互斥 | 无 |

axixi 版宣传的"串流中切换捕获屏 / 调分辨率刷新率 HDR"需要主机端换用 StarCore 星核 1.2.0，**不是**本仓库的官方 Sunshine 基线。本次实测证明：**除该功能外，axixi 与官方 Sunshine `2026.516` 正常协作**——这条边界值得记住，不要把"某一个功能需要换主机端"误读成"整个客户端不能用"。
