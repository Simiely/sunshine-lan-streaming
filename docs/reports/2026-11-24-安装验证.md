# L1 通过：三项配置生效，一条判据被证伪

**TL;DR**：`2026.516.143833` 装上了，服务、自启、账户、防火墙、三项基线配置全部符合预期。但自检脚本报了一个 `FAIL`——查下来是**我的判据写错了**，不是环境有问题。顺带发现监听地址是 `0.0.0.0`，六个网卡全部可达 Web UI。

## 三项基线配置

`C:\Program Files\Sunshine\config\sunshine.conf` 写入后为三行，无 BOM：

```text
origin_web_ui_allowed = lan
upnp = disabled
dd_configuration_option = disabled
```

`/api/config` 返回验证（该接口只回显被显式修改过的项，不是全量配置）：

|---|---|
| `origin_web_ui_allowed` | `lan` |
| `upnp` | `disabled` |
| `dd_configuration_option` | `disabled` |
| `status` | `True` |
| `version` | `2026.516.143833` |

应用列表已就绪：`Desktop`（串整块桌面）与 `Steam Big Picture`，定义在 `config/apps.json`，411 字节。

## 被证伪的判据：C-01

自检报的是：

```text
FAIL C-01 没有 47984–47990 的监听
```

实际状态是**三个端口都在监听**，归属同一个 sunshine 进程：

| 端口 | 地址 | 用途 |
|---|---|---|
| 47984 | `0.0.0.0` | HTTPS（串流控制） |
| 47989 | `0.0.0.0` | HTTP（客户端连接） |
| 47990 | `0.0.0.0` | Web UI |

**47985–47988 是视频 / 控制 / 音频 / 麦克风流端口，只在串流会话建立时才出现。** 把它们写进"启动后必须全部监听"的判据，等于要求一个没有会话的宿主先开出流端口——永远不可能成立。

错在两处，都记在脚本里改掉了：

1. **时序**：服务进入 `Running` 后只等 2 秒就查端口。实测端口在 3–5 秒内才就绪，改为轮询最多 30 秒。
2. **判据**：从"47984–47990 全部"改为"47984 / 47989 / 47990 三个常驻端口"。

修正后重跑自检，三项 `OK`。

## 新发现：0.0.0.0 绑定与六个网卡

三个端口都绑在 `0.0.0.0`，即**监听所有网卡**。这台机器有六个 IPv4 接口（业务网段、ZeroTier、两个 VMware、热点、`vgate0`），意味着每个网段都能到达 47990。

`origin_web_ui_allowed = lan` 控制的是**来源判定**，不是**绑定哪块网卡**。它能挡住公网来源，但挡不住"同处一个虚拟网段"的设备——ZeroTier 网络里的对端，从它的视角看确实属于 `lan`。

这是待确认的风险，不是结论：

- 若只把 Web UI 当本机管理台用，`origin_web_ui_allowed = pc` 更合适（仅本机可达）。
- 若需要手机打开 Web UI 看状态，就得保留 `lan`，但要接受 ZeroTier / 虚拟机网段同样可达。
- 首版先维持 `lan`，等 L3 用手机实测后再定。**不要因为"反正是内网"就跳过这一条**——六个网卡里有两个是第三方远程软件装的。

## 一个顺手验证到的幂等行为

重跑安装脚本时，它识别出"已安装 2026.516.143833，版本与目标一致"，跳过 `msiexec`，只做配置与自检。这意味着 zip 可以放心重复执行，不会反复装卸。

## 怎么验证

```powershell
# 端口应按判据返回三个常驻项
Get-NetTCPConnection -State Listen | Where-Object { $_.LocalPort -in 47984..47990 } |
  Select-Object LocalAddress, LocalPort, OwningProcess

# 配置应回显三项
curl.exe -k -s -u "admin:<密码>" https://localhost:47990/api/config
```

若 `Get-NetTCPConnection` 只有部分端口，先等 5 秒再查；30 秒后仍缺，才是真问题。
