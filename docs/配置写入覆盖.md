# 用 API 改一个键，会把其余键一起清空

**TL;DR**：`POST /api/config` 的语义是"用我给你的这份配置替换掉现有配置"，不是"把这几项改成新值"。只发 `{"output_name": "..."}` 的结果是：`output_name` 改对了，`upnp`、`origin_web_ui_allowed`、`dd_configuration_option` 全部消失，并且**回落到各自的默认值**——其中 `upnp` 的默认值是 `enabled`。

## 为什么危险

不是"配置少了几行"这么轻。三个键的默认值恰好都不安全：

| 键 | 缺失时的默认 | 后果 |
|---|---|---|
| `upnp` | `enabled` | 主动向路由器请求开放 47984–47990，可能把 Web UI 暴露到公网 |
| `origin_web_ui_allowed` | `wan` | Web UI 来源限制形同虚设 |
| `dd_configuration_option` | `disabled` | 唯一一个"缺失反而正确"的，纯属运气 |

也就是说，**一次看似无害的单键修改，会把安全基线整体回滚**，而且没有任何报错、没有任何日志提示。本机因此中招两次。

## 怎么认出它

三个信号，出现任意一个就去查文件：

1. `sunshine.conf` 字节数异常小（本机出问题时是 41 字节，正常应有 5 个以上键）；
2. `Get-Baseline.ps1` 的合格数凭空下降，且下降的正是 `D-02` / `D-03`；
3. 基线键明明写过却读不到——注意要看**文件内容**，不要看 Web UI 界面上显示的值，界面读的是内存。

## 正确做法

改 `sunshine.conf` 一律走合并写回：

```
读出全部键 → 覆盖目标键 → 其余键原样保留 → 写回 → 回读校验
```

`payload/scripts/Restore-Baseline.ps1` 就是这么实现的，可以反复执行，不会丢 `locale`、`output_name` 这类用户键。它额外做了三件必须做的事：

- **先停服务再写文件**。服务退出时会用内存里的旧配置覆盖文件，写完再停等于白写。
- **无 BOM 写入**。带 BOM 时 Sunshine 会把 BOM 并进第一个键名，该键静默失效。
- **轮询三个常驻端口**（`47984` / `47989` / `47990`），而不是启动后立刻判定。端口要 3–5 秒才起监听，早判会得到假阴性——这个坑在 `C-01` 上踩过一次。

## 如果不得不用 API

需要动态生效（例如改 `output_name` 后立即重连验证）时，请求体必须**带齐当时文件里的全部键**，一个都不能省。改完立刻 `Get-Content sunshine.conf` 回读，确认键数没有变少。

`upnp` 这类只在启动时初始化的项，即使 API 接受写入也不会立即生效，必须重启服务——所以它本来就不适合走 API。
